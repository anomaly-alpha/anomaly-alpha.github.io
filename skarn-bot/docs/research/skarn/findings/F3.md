## 2. Memory stores

The codebase intentionally maintains **5 distinct memory stores** (documented in `CONTEXT.md` §6.1) plus a 6th — `server_culture`. They differ in scope, write path, and read path.

### 2.1 `memory_entries` — the unified user memory (etch / extracted / conversation)

- Single table for ALL per-user memory, discriminated by `source` column: `CHECK(source IN ('etch','extracted','conversation'))` (`skarn-schema.sql:328`) and `CHECK(type IN ('fact','interest','project','event','preference'))` (`skarn-schema.sql:329`). The UNIQUE key is `(user_id, guild_id, type, content)` (`skarn-schema.sql:336`).
- **`source='etch'`** — user-intended facts via `/etch`. Written by `etch.handler.js:11` with confidence hardcoded to `1.0`. Re-etching the same fact bumps it back to 1.0 (`database.js:560`). Etched facts are **exempt from confidence decay** — `decayMemoryEntries()` only touches `source='extracted'` (`database.js:601`). Permanent until `/forget`.
- **`source='extracted'`** — auto-extracted entities from conversations. Written by the post-processor (`features/preprocessing/postProcessor.js:47-48`) via `addMemoryEntry(...,'extracted',...)`. The extraction is an LLM call (`gpt-4.1-mini`, temperature 0.2, `postProcessor.js:26,37`) run by `memoryExtractor.js` → `postProcessConversation()`. The prompt only advertises the 5 storable types (people classified as `fact`, `postProcessor.js:30`); any off-list LLM drift is **coerced to `'fact'`** (`postProcessor.js:11,47`) because a CHECK violation would drop the entire batch (a fixed 2026-08-02 production bug, `CONTEXT.md` §9.7).
- **Confidence lifecycle** (extracted only): starts at 0.5 (`database.js:568`), reinforced +0.1 per repeat up to 1.0 (`database.js:560`), decays ×0.95 after 30 days idle, pruned below 0.2 (`database.js:599-604`). A dedicated index `idx_memory_decay(last_seen_at, confidence)` serves the decay pass (`skarn-schema.sql:340`).
- **`source='conversation'`** — reserved for future conversation-derived memory; legal per CHECK but currently never written (`CONTEXT.md` §6.1, `DATABASE.md:142`).
- Read paths: `getMemoryEntries()` (top-10 by confidence) feeds the AI system prompt `memoryLine` (`features/promptContext.js:42`); `getMemoryByType()` feeds `knowledgeGraph.formatKnowledge()` (`features/intelligence/knowledgeGraph.js:4-6`); `getUserFacts()`/`getExtractedEntities()` feed `/memory` display (`memory.handler.js:15,29`); `getMemoryEntries()` also powers the `get_memory`/`etch_memory` AI tools (`features/tools/toolRunner.js:43`).
- `/forget` wipes all `memory_entries` for the user+guild in one delete (`features/forget/forget.handler.js:4`).

### 2.2 Conversation graph (threads + messages + summaries + FTS5 + embeddings)

- Raw message history, deliberately **separate from extracted facts** (`CONTEXT.md` §6.3). Threads auto-expire: 30 min for channels, 24 h for DMs (`database.js:125-126`, `getActiveThread` `database.js:128-138`; mirrored in `messageStore.js:6-7`).
- Write path: `storeMessage()` (`features/conversation/messageStore.js:50-86`) — commit message immediately with a placeholder `['general']` topic, then **backfill topics and embedding in the background, non-blocking**, because the topic extraction is a live OpenAI call that must not delay the reply (`messageStore.js:57-65,70-83`).
- Topic extraction: LLM returns 1-3 lowercase tags, bucket `'topic'`, temperature 0.2, fallback `['general']` (`features/conversation/topicExtractor.js:5-35`). Token estimate is a crude `length/4` heuristic (`topicExtractor.js:37-39`).
- Summaries: archived threads with ≥3 messages are AI-summarized after 7 days (`features/conversation/summarizer.js:4,8,13`; LLM temperature 0.3, 200 max tokens, last-20-messages window `summarizer.js:27-39`). Stored in `conversation_summaries` with `covers_from`/`covers_to`/`message_count` (`skarn-schema.sql:183-192`).
- Search: `conversation_fts` is an FTS5 virtual table manually kept in sync — every `insertMessage()` also writes the FTS row (`database.js:174-180`), and pruning deletes matching FTS rows by rowid (`database.js:312-314`). Queries are **sanitized** so FTS5 operator characters can't throw syntax errors (`database.js:342-344`).
- Retention: messages older than 90 days are pruned daily (`database.js:303-317`, scheduler `index.js:88`); `/forget` cascade-deletes threads, messages, summaries, FTS and embeddings (`database.js:321-336`).

### 2.3 Knowledge base (global)

- `knowledge_base` is the **only truly global memory store** — no user/guild scope columns (`skarn-schema.sql:281-290`), unlike every other table which follows the `(user_id, guild_id)` scoping rule (`CONTEXT.md` §3). Source: seeded Wikipedia topics (`knowledgeSeeder.js`) + user-taught facts via `/learn` (`CONTEXT.md` §6.1).
- Upsert semantics: `INSERT ... ON CONFLICT(topic) DO UPDATE` refreshes summary/source/confidence (`database.js:414-425`), then syncs its own FTS5 index `knowledge_fts(topic, summary)` (`database.js:426-435`). Read path is FTS `MATCH`, ordered by confidence (`database.js:438-448`); the feature wrapper adds a source icon for wikipedia/user_taught/generic (`features/knowledge/knowledgeBase.js:18-23`).

### 2.4 Omen prophecies and 2.5 Chronicle — see §4.

### 2.6 What is NOT in these five: the "7th store" split

`user_emotional_context` (transient emotion, overwritten per mood check — `database.js:462-472`) and `realm_npc_memory` (in-fiction NPC memory, consumed only by the Realm game, never injected into Skarn's system prompt — `CONTEXT.md` §6.1) are separate by design. `CONTEXT.md` §6.3 notes the fragmentation in the now-removed `user_memory`/`knowledge_graph` tables was an accident, not a design choice.

## 3. Channel state machine

### 3.1 The four states

`channel_state` (`skarn-schema.sql:2-10`) tracks a per-channel mood machine: **Dormant / Attentive / Charged / Weathering**. Each state carries a prompt directive via `STATE_LINES` (`features/channelState/stateTracker.js:9-14`):
- **Dormant**: "the channel has been quiet a while. Be more observational, ask fewer questions, keep it terse."
- **Attentive**: normal conversational energy.
- **Charged**: "the room is heated or moving fast. Be sharper and shorter, more opinionated."
- **Weathering**: "someone nearby has been venting... Be steadier, less witty."

The state line is injected into the AI context by `features/promptContext.js:37` and is read by ~20 command files (e.g. `commands/roast.js:6`, `features/vein/vein.handler.js:76`).

### 3.2 Transition rules

- **On every message** (`onMessageReceived`, `stateTracker.js:24-71`): state is recomputed with priority order — `Charged` if ≥8 messages in a 5-minute window (`CHARGED_THRESHOLD=8`, `CHARGED_WINDOW_MS=5min`, `stateTracker.js:5-6,49-50`); else `Weathering` if the sentiment-buffer average drops below −0.3 (`WEATHERING_THRESHOLD`, `stateTracker.js:7,52-55`); otherwise `Attentive`. It is a **single write per call** with exactly-once window/count computation (`stateTracker.js:38-43,58-70`).
- **Weathering detection input**: the last 5 message texts, stored in SQLite `sentiment_buffers` (`database.js:646-656`) — an explicitly ephemeral thing that is persisted anyway ("All state in SQLite" convention). Comparative scores are memoized in an in-memory `scoreQueues` Map with a cold-path rebuild from the persisted buffer (`features/channelState/sentimentBuffer.js:7,21-32`).
- **Decay pass** (`features/channelState/stateDecay.js:7-29`, run every 10 min from the scheduler `features/scheduler/index.js:77`):
  - Charged/Weathering revert to **Attentive after 30 min** of no transition (`stateDecay.js:4,11-16`).
  - Any non-Dormant channel with **6+ hours since last message** becomes **Dormant** (`stateDecay.js:5,20-25`).

### 3.3 Why Dormant is ONLY set by the decay pass

This is a load-bearing invariant with a documented bug history:
- `stateTracker.js:44-46` explicitly comments: "Dormant is intentionally NOT evaluated here — arriving traffic can never itself be 'Dormant'. Dormant is only ever set by runDecayPass() during genuine idle periods."
- `stateDecay.js:18-19` is even stronger: "this is the ONLY place Dormant is ever assigned."
- Root cause (`CONTEXT.md` §9.3): an early version set Dormant when a message arrived after a long gap, creating a **permanent livelock** — message → Dormant → decay pass sees Dormant and does nothing → next message also sees Dormant. Dormant must mean "no messages at all", not "messages arrived after silence". Removing the decay pass would leave channels stuck in their last state forever (`CONTEXT.md` §7.6).

## 4. Omen & chronicle (server-memory narrative layer)

### 4.1 Pipeline: signals → chronicle/omens

Raw "notable events" are captured as `server_signals` (`skarn-schema.sql:545-554`):
- **Realm milestones** — quest complete, level-up, boss defeated (`features/realm/quest.js:85`, `features/realm/character.js:141`, `features/realm/combat.js:214`), gated on `memory_optout.chronicle_optout` (`signalCapture.js:47-49`).
- **Reaction spikes** — 5+ reactions on one message triggers a signal (`signalCapture.js:5-34`, threshold `REACTION_THRESHOLD=5`), skipped if the channel is in Weathering state (`signalCapture.js:19`).
- Signals are pruned after 30 days (`scheduler/index.js:96-98`), but the narratives built from them persist.

### 4.2 Chronicle — weekly narrated history

- `chronicleJob.js` runs daily (scheduler `index.js:100-102`), but only actually generates when: (a) ≥7 days since the last entry's `period_end` (`CHRONICLE_INTERVAL`, `chronicleJob.js:8,14`), and (b) ≥3 signals captured in the window (`MIN_SIGNALS`, `chronicleJob.js:9,16-17`).
- The LLM is prompted with realm milestones listed first ("Realm events this week") then other notable moments, and asked to "write a chronicle entry for this week in Skarn's voice" (`chronicleJob.js:20-28`), temperature 0.8 (`chronicleJob.js:37`). Output is stored in `chronicle_entries` with `period_start`/`period_end` (`chronicleStore.js:3-7`) and posted to the configured channel.
- User surface: `/chronicle show|history|generate|setchannel|optout` (`chronicle.command.js:4-12`).

### 4.3 Omens — AI prophecies matched against real events

- `omenJob.js` runs daily and posts a new prophecy when: under 10 unresolved (`MAX_UNRESOLVED`, `omenJob.js:10`), ≥4-7 days since the last one (a **randomized** posting interval from `omen_min_interval`/`omen_max_interval` guild config, `omenJob.js:67-71`). Generation is high-temperature (0.9, `omenJob.js:28`) to be cryptic.
- **The distinctive part**: an omen is *fulfilled by embedding similarity*. Every omen is embedded (`embedText`, `omenJob.js:74`); every signal since the omen's creation is also embedded (cached in `signal_embeddings`, `omenJob.js:94-99`). If cosine similarity ≥ 0.7 (`MATCH_THRESHOLD`, `omenJob.js:12`), a second LLM call generates a callback narrative connecting the prophecy text to the real event (`generateCallback`, `omenJob.js:39-56`), and the omen transitions `unresolved → fulfilled` with `fulfillment_text` and `resolved_at` (`omenStore.js:15-19`). Unmatched omens expire after 30 days (`OMEN_EXPIRY_MS`, `omenJob.js:11,117-119`).
- **Manual fulfillment**: `/omen fulfill <description>` embeds the user's text and matches against unresolved omens (also threshold 0.7), capped at 5/day per user via `app_flags` (`omenJob.js:135-179`).
- **Realm crossover**: fulfilled omens are recorded in `realm_omens` (`skarn-schema.sql:610-615`, `omenStore.js:39-43`) so prophecy callbacks become in-fiction Realm history (`omenJob.js:107-109,170-173`).
- Signals can't be matched until the omen is ≥24 h old (`MIN_OMEN_AGE_MS`, `omenJob.js:13,86`).
- User surface: `/omen show|fulfill|history|setchannel|frequency` (`omen.command.js:4-12`).

## 5. Distinctive choices

1. **"All state in SQLite" is a hard convention** — even ephemeral, restart-transient data is persisted: sentiment buffers (`database.js:646-656`), every cooldown type (`database.js:617-642`, `794-803`), banter chains (`database.js:734-751`), callbacks (`database.js:755-766`), attention counters (`database.js:857-878`), app flags with TTL (`database.js:665-719`). The former in-memory cooldown Maps (reaction, search, warmth, realm, omen) were migrated to SQLite-backed cooldowns in the 2026-08-01 audit (`CONTEXT.md` §2, §3). `database.js:14-19` sets WAL + foreign keys for crash recovery.

2. **What is still in-memory by design** — all of it is *session-volatile*, explicitly listed in `CONTEXT.md` §2/§3: `activeCombats` (realm/combat), `activeTrades` (realm/economy), `activeGames` (games/tetris), `banterChains`/`setups` (humor/comedyTiming), plus the per-message reaction counter Map (`signalCapture.js:5-7`), the sentiment `scoreQueues` Map (`sentimentBuffer.js:7`) and the TTL-cached lorebook list (`database.js:888-890`). The invariant is that no *cooldown* or *durable fact* is in-memory — game sessions are meant to die with the process.

3. **Confidence-driven forgetting is asymmetric**: user-committed facts (`etch`) are permanent and decay-exempt; machine-extracted facts are automatically forgotten (0.95×/30d, pruned <0.2). Decay SQL is a single pass `UPDATE ... confidence*0.95 WHERE source='extracted' AND last_seen_at < cutoff` then a prune DELETE (`database.js:599-604`).

4. **The `Dormant` invariant** (§3.3) — silence is a state only *computed by the absence of messages*, never by a message handler — plus the "single write per call" rule in `stateTracker.js:58-70` to avoid read-modify-write races (`CONTEXT.md` §9.1).

5. **Fragmentation-with-purpose**: 5 deliberately separate memory stores with different scopes (per-user vs. per-thread vs. global vs. per-guild narrative), never merged — `CONTEXT.md` §6.3 documents that merging was considered and rejected because write/read/query patterns differ.

6. **Omen/chronicle invert the usual memory direction**: instead of storing facts *about* users, they store *narratives about the server* (prophecies, weekly chronicles) derived from a thin `server_signals` event log, and they close the loop with embeddings — an LLM prophecy is matched to real-world events purely by vector similarity (0.7 threshold), then an LLM "fulfills" it. Server history is thus generated, not just recorded.

7. **Two hand-synced FTS5 indexes** (`conversation_fts`, `knowledge_fts`) maintained manually in `database.js` (insert at `174-180`, delete at `312-314` for messages; delete+insert at `426-435` for knowledge), with query sanitization to survive Discord's operator-heavy text (`database.js:342-344`).

8. **The schema encodes invariants in CHECK/UNIQUE**: `source`/`type` CHECK constraints on `memory_entries` (`skarn-schema.sql:328-329`) are treated as the source of truth — the LLM-driven extraction layer whitelists/coerces to them (`postProcessor.js:11,47`) after a production CHECK-violation crash (`CONTEXT.md` §9.7).

9. **Deliberately no test framework** and no CI — verified manually; the `tests/` directory was removed by decision (`CONTEXT.md` §11.2). The schema, DATABASE.md and CONTEXT.md together act as the living spec.
