# F5 — Human-ness Emulation & Safety/Moderation Systems

Research angle for **skarn-bot** (`/Users/prime/Sites/Gems/anomaly-alpha/skarn-bot`).
How the bot fakes being human (typing, reactions, edits, interjections, proactivity,
"reaction-only mode"), the probabilistic attention gate, its moderation stack, and the
preprocessing pipeline. All claims cite `file:line` relative to the skarn-bot root.

## 1. Authenticity layer (simulating human behavior)

### 1.1 Typing simulation (`features/discordNative/typingSim.js`)
- **Delay scales with response length**: short (<100 chars) → 500–1500 ms; medium (<300) → 1000–3000
  ms; long → 2000–4000 ms (`typingSim.js:1-5`).
- `simulateTyping` calls `channel.sendTyping()` then sleeps the computed delay
  (`typingSim.js:7-15`). Permission failures are swallowed (`typingSim.js:12-14`).
- **Keepalive**: because Discord's typing indicator expires ~10 s after the last `sendTyping`,
  `startTypingKeepalive()` pings immediately then refreshes on an 8 s `setInterval`, returning a
  `stop()` to clear it (`typingSim.js:17-33`). This makes the indicator stay visible for the
  ENTIRE AI thinking duration, not just the pre-send pause. Wired at the very top of
  `sharedPipeline.js:57` and stopped in `finally` at `sharedPipeline.js:246`.
- A second, redundant delay is computed by `features/authenticity/typingController.js`
  `estimateDelay()`: per-char rate (15 chars/s base, ~8 slow), jittered, clamped 500–4000 ms
  (`typingController.js:6-14`). Called before sending (`sharedPipeline.js:199`). Note the two
  typing systems coexist: typingController's `estimateDelay` is used alongside typingSim's
  `simulateTyping` in the pipeline — stacking delays.

### 1.2 Passive emoji reactions — TWO independent systems
- **`discordNative/reactionSystem.js`** (fires on every tracked message): 3% base chance
  (`reactionSystem.js:6`), skips negative sentiment (`comparative < -0.5`, line 16), 60 s per-channel
  cooldown (`reactionSystem.js:5,20`), prefers a random guild emoji 50% of the time else pulls from a
  6-emoji standard pool (`reactionSystem.js:30-39`). Sleep-aware: only runs when not asleep
  (`bot.js:306-320`).
- **`authenticity/reactionController.js`** (reaction-ONLY mode, see §1.6): 10% chance for casual
  intents, sentiment-selected emoji pools (positive/negative/neutral) (`reactionController.js:1-26`).
- So there is a low-probability 3% ambient reaction layer plus a 10% "reply the user by emoji only
  instead of text" layer — two distinct probabilities (3%"ish" passive vs 10% reaction-only).

### 1.3 Message editing (`features/authenticity/messageEditor.js`)
- **5% chance to "edit" a just-sent message** (`messageEditor.js:20`), capped at 2 edits/hour
  (`messageEditor.js:2`), delay 500–2500 ms after posting (`messageEditor.js:4-5`).
- The edit is humanizing: 40% capitalize first letter; 70% add a period; <90% append an afterthought
  like " lol / tbh / fr / ngl" (`messageEditor.js:23-40`). Rates are pushed via stack-style
  `editTimestamps` array pruned to a 1-hour window (`messageEditor.js:9-15`).
- Only wired into the `/consult` (slash) path: `consult.handler.js:2,50-51`; the mention/auto-respond
  path passes `scheduleEdit` (a no-op callback, `sharedPipeline.js:215,222`) so edits only occur on
  slash-consult replies.

### 1.4 Interjections (`features/presence/interjectionEngine.js`)
- Fires on ambient (non-mentioned) messages with a **tiered friendship chance**: 0.5% base; 10% if the
  user is tagged `regular` AND the message reads as banter; 8% if tagged `veteran` AND contains a `?`;
  unknown users held at 0.5% (`interjectionEngine.js:28-33`). Gated by a per-channel 5-min cooldown
  (`interjectionEngine.js:23`, table `interjection_cooldowns`).
- The interjection itself is an in-character LLM reply tempered by a prompt "glancing up and saying
  something" with `temperature 0.85`, max 100 tokens (`interjectionEngine.js:38-51`), with hard-coded
  fallback lines like "bruh moment 😔", "based", "i saw that 👀" (`interjectionEngine.js:7`).
- Sleep-aware and opt-in-gated via the shared `canInteract` (`interjectionEngine.js:19-20`).

### 1.5 Reaction-only mode (10%)
- `shouldReactOnly(intent)` returns true 10% of the time ONLY for `['casual','sharing','banter','greeting']`
  intents (`reactionController.js:9-13`). 
- In `mentionRouter.js:33-38`, an @-mention whose cleaned text is "casual" can be answered with ONLY an
  emoji reaction (`message.react(pickReaction(sentiment))`) instead of any AI call — the AI pipeline is
  skipped entirely. This is a cost-lowering AND humanizing mechanism (CONTEXT.md §7.4 frames it as
  adding a natural "busy" behavior and reducing spend on low-stakes pings).
- Note: `shouldReactOnly` is only ever called with the hard-coded literal `'casual'` (`mentionRouter.js:35`),
  so the other accepted intent strings are dead API surface.

### 1.6 Casual flavor post-processing (`features/discordNative/postProcess.js`)
- Applied only to `search` role output (`postProcess.js:74`; `search.handler.js:74`,
  `commands/search.js:77`); NOT applied in the shared pipeline path.
- Style layers: 30% lowercase-first-letter; per-role chance to strip a trailing period
  (casual 60%, moderate 20%, default 10%); 15% append an abbreviation (" fr/ngl/tbh/imo"); 10% append
  a casual emoji (`postProcess.js:9-18,23-52`). None fire on text > 200 chars.
- Long replies are sentence-split to chunks and **"burst"** asynchronously with a 2–4 s natural gap
  between the first chunk and the tail (`postProcess.js:54-83`).

## 2. Attention gate — when to respond unprompted (`features/discordNative/attentionGate.js`)

`shouldRespond()` decides whether the bot chimes in on a NON-mentioned message in an AI-enabled
channel (`bot.js:324,342-347`). It is a mix of deterministic early-exits and a **probability-stacking
model**:

**Always-respond early exits (return true):**
1. User replied to one of Skarn's own messages (`attentionGate.js:14-19`).
2. Recency boost: Skarn responded to this user within 2 min (`RECENCY_MS=120000`; line 28-29).
3. Channel warm: Skarn spoke in this channel within 30 s (`CHANNEL_WARM_MS=30000`; line 31-32).

**Additive probability stack (summed into `probability`, then `Math.random() < min(prob,1)`):**
- **Question/"skarn" heuristic: +0.6** if content contains `?` or the token `skarn` (`line 39`).
- **Message-count escalation: 0.6 at 3 msgs, 1.0 at 5** — `min(msgs_since_response/5, 1.0)`
  (`lines 41-43`). Tracked per user/guild/channel in `attention_state` (`afterReply` resets it,
  `mentionRouter.js:66-74`).
- **Channel-activity decay: slow channels get a boost** — `max(0, 0.3 - rate*0.1)` where rate is
  msg/min over a 30-min window (`lines 45-51`). Busier channels → lower add.
- **Sentiment boost: +0.4 for angry/stressed/sad, +0.2 for anxious** via existing emotion detection
  (`lines 53-60`).

**Fallback tier:** when the statisken sum is too low, it makes a **tiny 5-token temperature-0.1 AI
YES/NO call** — "Would the bot have something relevant to say?" (truncates message to 200 chars;
`lines 64-78`). So even a low-probability channel message can get a "hand-raise" from the LLM.

Retrogaded correctly in CONTEXT.md §7.7, which frames this as "the primary gate for non-reply,
non-mention AI responses."

## 3. Proactivity — check-ins, absence detection, scheduler

### 3.1 Absence detector (`features/proactive/absenceDetector.js`)
- Finds "regulars" gone 3+ days with ≥10 lifetime interactions, ordered by familiarity
  (`ABSENCE_THRESHOLD_MS = 3 days`, `MIN_INTERACTIONS = 10`; `absenceDetector.js:3-13`).
- Check-ins are **opt-in only**: `proactive_opt_in === 1` required, and no check-in may repeat within
  3 days (`absenceDetector.js:15-25`). The shared `canInteract()` is the single opt-in gate used by
  mentions, interjections, and active listening (`absenceDetector.js:36-40`).
- Check-in copy is a canned per-user message ("hey <@u>, been a minute 👀") — not AI
  (`absenceDetector.js:27-34`).

### 3.2 Scheduler (`features/proactive/scheduler.js`)
- Ticks every 10 min (`scheduler.js:5`). Every 3rd tick (~30 min) scans all guilds for absent regulars
  (`scheduler.js:22-46`). Sends each check-in to the system channel, then `general`, then any usable
  text channel (`scheduler.js:73-86`).
- **Daily dial-down**: a hard cap of 1 proactive message per user per day, counting both `'sent'` AND
  `'failed'` records (`DAILY_PROACTIVE_LIMIT=1`; `scheduler.js:6,49-57`). Failures are recorded so a
  bad channel doesn't let the same user get re-messaged (`scheduler.js:66-71`).
- Opt-in is auto-enabled for DM users (`bot.js:190-195`) — proactive behavior is opt-out in DMs but
  opt-in in servers.

### 3.3 Active listening (`features/warmth/warmthManager.js`)
- On long (>200-char) messages from users with familiarity >15, in NON-AI channels only, a **5% chance**
  to emit a listening cue like "mhm", "yeah?", "go on", "i'm listening" (`warmthManager.js:105-141`),
  preceded by a 2–4 s "Skarn is reading" delay (`warmthManager.js:135`), per-channel 5-min cooldown
  (`warmthManager.js:122`, `active_listen_cooldowns`).

## 4. Safety & moderation systems

### 4.1 Slur filter / hostile-language 3-strike silence (`features/safety/slurFilter.js`)
- 10 hostile regexes (`shut up`, `stupid bot`, `f*ck you`, `fuck you`, "you're useless", `bad bot`,
  `worthless`, `kill yourself`, `go die`) (`slurFilter.js:11-15`). Input-only.
- **Strikes tracked per-user in `app_flags` key `strike_{userId}`** with a 10-min sliding window
  (`slurFilter.js:5,33-48`); at 3 strikes the user is silenced for 10 min (`slurFilter.js:6,57-59`).
- Enforcement is **centralized**: `isSilenced(userId)` is checked inside `moderatedChatCompletion()`
  before ANY AI call (`ai/client.js:49-51`), returning a static de-escalation line
  (`slurFilter.js:72-82`) — no AI spend, no model call. Additional pre-checks fire in the mention
  router (`mentionRouter.js:24-31`) and consult handler.
- Gates 2 & 3 note (CONTEXT.md §13): the old `slur_filter` table + LLM seeding were deleted
  (2026-08-01); the only remaining "gate" besides the strike system is a prompt-instruction safety
  line (`slurFilter.js:27-29`) + OpenAI moderation.

### 4.2 Moderation fail-closed (`ai/client.js`)
- Every AI call runs through a single choke point `moderatedChatCompletion()` (`ai/client.js:41`).
  Moderation is a genuine **fail-closed** design:
  - Input check `moderateInput()` (`ai/client.js:14-39`) maps self-harm categories to a `crisis`
    action (`ai/client.js:19-21`); OTHER flagged categories that are not whitelisted violence →
    `block` (`ai/client.js:22-32`). **On moderation API error it fails to `block` with
    `unavailable`** (`ai/client.js:35-38`) — not open.
  - Output moderation: if OpenAI's `moderation.output` has an error OR is unavailable, the call
    **fails closed** with `safeMessage: getSafeMessage(null, true)` (`ai/client.js:113-121`).
  - Rate-limit/silence checks run before the AI call and short-circuit with a safe message
    (`ai/client.js:49-55`).
- **Deliberate violence allowance**: violence/graphic/harassment categories are explicitly allowed
  through because Skarn "tells battle stories in-character" (`ai/client.js:24,99`); everything else
  (hate, sexual, minors, etc.) is blocked via `safeMessages.js` (`safeMessages.js:1-19`).

### 4.3 Crisis response lines (`features/safety/crisisResponse.js`)
- A static **ephemeral** message (flags:64 = private to user) directing to 988, Crisis Text Line,
  IASP directory (`crisisResponse.js:3-14`), signaled from `moderatedChatCompletion` returning
  `{ success:false, crisis:true }` (`ai/client.js:58-62,90-96`). Wired into ~20 command/handler
  call sites (e.g. `consult.handler.js:54-56`, `search.handler.js:68`, `slurFilter` interjection
  fallback `interjectionEngine.js:55`). Privacy: ephemeral so only the flagged user sees the resources.

### 4.4 Safe-message handling (`features/safety/safeMessages.js`)
- Maps moderation categories to static in-character refusals ("I don't do hate…" for hate,
  "I can't process that request." for sexual) + a `MOD_UNAVAILABLE` string ("Something's off with my
  connection") when moderation is unavailable yet the code failed closed (`safeMessages.js:1-19`).

## 5. Preprocessing pipeline (`features/preprocessing/`)
Four-stage vertical slice invoked from `sharedPipeline.js:69-93`:

1. **Retriever** (`retriever.js:5-61`) — pulls conversation history (tiered: 15 msgs full / 3 light,
   `retriever.js:14-37`), optional KB via analyzer-picked search terms (`retriever.js:40-44`), memory
   only when the analyzer says relevant (`retriever.js:46-53`), user profile + channel activity
   (`retriever.js:21-29,56-58`).
2. **Analyzer** (`analyzer.js:27-69`) — one LLM pass (`gpt-4.1-mini`, temp 0.1, JSON schema) classifying
   intent/sub-intent/emotion/tone/topics/entities, plus `safety_flags`, suggested tier, and a
   `context_prune` list of context lines to drop (`analyzer.js:4-24`). Retried once on failure
   (`pipeline.js:14-21`).
3. **Assembler** (`assembler.js:3-28`) — builds the system prompt: stable SKARN_CORE_IDENTITY + role +
   stable analysis lines first, dynamic conversation/channel lines last (`assembler.js:4-19`).
4. **PostProcessor** (`postProcessor.js:13-54`) — extracts storable memory entities from the exchange
   with a second LLM pass; coerces any off-schema type to `fact` so one bad entity can't drop the batch
   (`postProcessor.js:10-11,44-49`). (Explicitly FILE-level trivia: this is the same name "postProcessor"
   as `discordNative/postProcess.js`, but they are unrelated — the native one does casual styling.)

`pipeline.js:5` lists `CHEAP_COMMANDS` (`joke/roast/insult/pickup/compliment/meme/vein/search`) and
`pipeline.js:11-12` skips skip-listed commands and anything < 10 chars.

## 6. Distinctive choices

1. **Two stacked typing systems.** `typingSim.startTypingKeepalive` keeps the Discord indicator alive
   for the whole AI call, then `simulateTyping` + `typingController.estimateDelay` add MORE delay before
   send (`sharedPipeline.js:13,57,196,199,246`). Belt-and-suspenders "human" pacing.
2. **Three-tier moderation:** regex strike system (prompt/hostile), deterministic safety lines, AND
   OpenAI nested moderation — all converging on ONE chokepoint `moderatedChatCompletion`
   (`ai/client.js:41`), which is **fail-closed on moderation errors** and silently **allow-lists
   violence** so the in-character demon can talk about battles (`ai/client.js:24,99`).
3. **Symmetric human failure:** the bot edits its own messages (~5%), react-onlys (~10%) instead of
   answering, interjects only when "familiar", and adds casual networks' filler ("fr/ngl/tbh") — i.e.,
   it deliberately performs *lower* competence to be believable, trading correctness for foot-feel.
4. **Proactivity is fundamentally opt-in** (`proactive_opt_in`), with a strict 1/user/day budget that
   also counts FAILED attempts (`scheduler.js:49-57`) — an unusually conservative anti-spam posture for
   an "absent-friend check-in" feature, while DMs auto-opt-in (`bot.js:190-195`).
5. **Attention gate is a true probability adder, not a rules engine:** recency + warmth early-exits,
   +0.6 question / escalation 0→1.0 / channel decay / +0.4 emotion boost, with a tiny 5-token LLM
   YES/NO fallback (`attentionGate.js:5-82`) — the cheapest possible AI signal to still catch relevant
   messages in slow channels.
6. **"No test framework" design.** Reviewer-visible only via docs (AGENTS/CONTEXT): tests were removed
   by decision; verification is manual. The human-simulation and safety layers carry knowledge that is
   centralized, not test-covered.
7. **Two reaction systems and two "post-processors" with the same name** are independent —
   an easy iconfusion trap for anyone extending the codebase (`reactionSystem.js` vs
   `reactionController.js`; `discordNative/postProcess.js` vs `preprocessing/postProcessor.js`).
